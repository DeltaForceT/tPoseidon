# Changelog

Every release is listed here, newest first. Versions look like `0.MINOR.PATCH-beta`; [BETA.md](docs/beta/BETA.md) explains what the numbers mean. Back up your database before every update. A release that changes the database says so at the top.

## 0.84.4-beta

No database change. The first start after this update rebuilds the server data once (the world snapshot), which takes a little longer than a normal start.

### Added

- Item details in the GM item pickers (issue 133): in the panel's GM window, every place where a GM picks an item (Players > give item, My Camp items, Spawn > give item, presents) now has a details box to the right of the picture. Hover over a row or click it and the box shows the item's name, id, game data table, category with its type and subtype, where it is worn, the level and stat it needs, the species and jobs that can use it (for example "Raccoon: Student Teacher, Card Master, Dark Lord", with the names the game data holds), its stat bonuses with the names the client shows for them (AP, AC, DX, Max. MP and so on, read from the game data), stack, its time limit (the real duration from the game data's timed item table, for every item that has one), options, reforms, compound slots, weight and value. Drills also show their level, depth and durability. The details are built only for the row you point at, so the lists with thousands of items stay as fast as before.

- Game window choice (issue 132): the launcher now shows the resolution and a Full screen box right above the Play button, and the panel has Game window (Play) in its menu (the three dots), for the host's own Play button. The original client has no resolution option in its own game; it reads two values at start, widthPixel and heightPixel, and its setup tool offers exactly 800 x 600 and 1024 x 768 next to Full Screen Mode, so those are the only two I offer, in a window or full screen. I write the choice into the client's own settings (the Setup key of its registry profile, only those three values) just before the client starts, and the launcher remembers it in its settings file. Until you pick something, the box shows whatever the client has stored and I write nothing. Saving the Options page in the launcher updates the same choice. Checked in the game by starting the original client with each of the four combinations.

### Fixed

- PvP target rules for skills and the hit on a player (issue 144, second part): I read the original's attackable test (0x5E6D70 in the KR Server) and now use it for every player target: the attacker's PvP mode decides (0 never; mode 1 needs the target in mode 1, not in the attacker's party, and the attacker not in peace mode; mode 2 needs the duel opponent; modes 3 and 4 attack each other), which replaces my earlier rule of only checking that the attacker's mode is 1 to 4. A skill used on a player now rolls the original's player hit chance (0x5E70C0 and 0x5E7150: attacker AC minus target HV plus 40 for physical skills, attacker LK minus target LK plus 90 for magic, kept between 20 and 90 percent). Area skills now also hit the players inside their radius, after the monsters and within the same limit, like the original's second pass for players. A player hit by a skill gets the frames the original's victim handler writes (0x73BDB0: the 0x002A hit record, no 0x011E and no 0x002B, with the peace-break notice before it and the death frames after it), and tests pin the order. Chain, object, throw and Polar combo skills are still monster only: the original's player passes for them are not decoded yet, so they still refuse a player target. Candidate fix, needs a live check with two clients.
- Lion could not attack a Polar in PvP (issue 144): in Desert Battleground (map 187, a PK zone) both players were put in PvP mode 1, and the plain melee swing already worked both ways, but the two other ways to hit a player were only built for monsters. A gun shot looked up its target in the monster list only and was refused when the target was a player, and a damage skill (Punch, Fairy of Magic, Mana Arrow and every skill that uses a hit shape) found no monster for the aimed id and was refused with code 0, which the client shows as the message that the condition is not met. The Polar's hammer is a melee swing, so it worked. A gun shot and those skills can now hit a player target under the same rule as the melee swing (the attacker's PvP mode must be 1 to 4, neither side is a guild game observer, the target is alive and not in another duel). The hit uses the same damage factor per PvP mode as melee (the table at 0x99C4B0 in the KR Server, read by 0x5E7050), the target's spawn protection, and the same death, peace mode and kill credit handling as the melee swing. Skills with their own special handling (area, chain, object, throw, heavy hit and the Polar hammer combos) are still monster only and still refuse a player target. Candidate fix: the frame order for a player target hit by a skill or gun shot is built from the monster frames without the monster hit points and death frames, and I have no capture of it, so it needs a live check with two clients.
- Hidden NPC names on the minimap (issue 141): the original client draws the minimap marks of the hidden NPCs (ids 17000 to 17998) only for a player who has the Mind's Eye effect, but the hover name box and the list the marks are collected in never checked it, so on every map the names showed when the cursor passed over their spot. The play button now also patches the KR 2014 client so that these NPCs are not added to the minimap list at all unless the effect is on (the same test the drawing uses: the id range and the Third Eye byte of the player). Like the address patch it checks the exact original bytes first, keeps the .tposeidon-original backup, does nothing twice and leaves a client it does not know untouched.

- Element line below the set lines in item tooltips (issue 143): the original client builds an item tooltip as stats, set equipment lines, then the element block (for example Electric Attribute +146%). Korean players report that it shows above the set lines, so the patch moves the element block to directly after the stats in both tooltip builders that have a set section. The other tooltip builders have no set section and stay as they are. Same safety as the issue 141 patch: exact original bytes, backup, once only.

- Wrong stat changes when comparing a cash box item (issue 142): an item taken out of the cash item box and hovered in the bag showed the negative of the worn item's stats in the compare section (Attack -144, Max HP -360). The take reply carries one record for the bag and one for the box, and I gave the bag item the same item id as the box entry. The client wipes the stored property list of an item id when a removal record arrives (removal case of 0x58E540 calls 0x590F70), and the compare section sums those lists only (0xACD890 over 0x591230), so the bag item lost its stats the moment the box record was applied. The bag item now gets its own item id from the item table when it is taken. Candidate cause: I could not reproduce it with the client here, and the unit tests cover the new id and the frame, not the tooltip itself.
- Summer daily quest offered in winter (issue 140): the 2014 data attaches each town daily-quest NPC (Stargazer Stella and the other twelve) to its summer dialogue table and summer quest (the NPC rows say NpcMsg_..._OnSu with a quest in the 6013 to 6025 range), and the data also holds the spring, autumn and winter versions (Quest_NpcMsg lists which quest goes with which table), so the summer quest stayed on offer all year. The server has no season check of its own, so I now pick the version for the current season (spring March to May, summer June to August, autumn September to November, winter December to February, by the server's clock) when the server starts; it follows the Quest_NpcMsg pairs and leaves an NPC alone when its season has no version (Oops Wharf has no autumn one). Restart the server when the season changes.
- Daily quests that could be done several times a day (issue 139): the once-per-day check that the original runs on its daily quest scripts (Quest_Once_Accept and MonQuest_Once_Accept, which cover the town daily quests, including the ones asking for 100 materials) compared the completion date with a date in the database, and that comparison never matched a stored time, so the quest could be accepted again right after turning it in. I now check whether the completion time falls inside today's span, and the day changes at midnight of the server's own clock, which is where the original resets its other daily counters. The completion date was already saved per character in the quest history, so nothing needs migrating.
- Server-wide announcements for a new job and for awakening (issue 138): when a player completes the job change to the third job tier, or the first guardian awakening, every player now sees "[Trickster] island name - player has advanced to job. Congratulations!" or the awakening line, queued through the same notice queue as the GM megaphone notice. This follows the original game server, which announces only the third-tier change (job above 16, 0x78A210) and the awakening in guardian slot 0 (0x79A230); the second-tier change is not announced there. The delivery step after the queue was not read in the original, so it is unconfirmed.
- Monsters now regain HP over time (issue 137): every 6 seconds a monster that is not fighting and not dead regains 8 HP, or the HpRegen value of its data row when that is not 0, never above its maximum, and it stops regaining while it is in a fight, as in the original (the original server's monster tick 0x729E20 calls 0x729DD0, which skips battle state, then 0x729C30 with a 6000 ms period; the amounts are set in 0x7287E0 from the spawn type value, which is -1 for every monster the original spawns, so 8 and 8). Monster MP is not tracked on my side, so MpRegen has no effect yet.
- Drill-kun pets arrived expired from the GM cash box (issue 127): Drill-kun 100 and 200 (15859, 15863) are time-limited items (ExistType 1) whose three-day period lives only in the GeneralTimerItem table, and they are in no shop. The GM cash box delivery (`present-box`, the Send to the cash box checkbox) took its period from the item shop only, so a time-limited item without a shop row went into the cash box with no end time, and the client then shows 사용 기간 종료 and refuses to equip it. The Drill-yang 60 pets (90115, 90116) are sold in the shop, which is why they worked. The cash box delivery now falls back to the GeneralTimerItem period, rounded up to whole hours, when neither Hours nor a shop period is given. Drill-yang 1616 (Driller Girl) never digs by itself because the data lists no AutoDrillPetInfo row for it: the original answers its auto-drill request with error 10, as the server does, and the pets that dig are 1557, 1566, 15859, 15863, 15886, 90115 and 90116.
- Character drawn without equipment after a transformation ends (issue 129): when Wild Mutation, Change or Beast ran out, or a disguise or wedding dress was taken off, I sent the stat reset and the form removal but never the appearance refresh. The original follows every form end with 0x0246 to the area: the entity id, then the equipment look block (mask and one item id per worn slot, as in the spawn) and the look override block (equipment_server.md 5.4, 0x5FEC70; skills_last_batch_spec.md 4.5 for Beast; transform_disguise_spec.md 2 for the disguise removal 0x0402 followed by 0x0246). The client redraws the equipment from it; without it the sprite stayed bare until the next map change, which resends the spawn. I now send 0x0246 with the real look after each of these ends (before this only the job change sent it, with empty blocks). Checked in the game with the original client: when Wild Mutation ended the server now sends 0x0246 with the entity and the worn ears and tail (items 6901 and 6951) after the stat reset, which the unfixed server did not send. I could not tell the drawn sprite apart reliably in my screenshots (the test character wore only ears and a tail), so the redraw itself is not checked.
- Transformed skills refused after Wild Mutation (issue 128): a Cat that transformed with Wild Mutation (Evolution, skill 4105) could not use any skill of the form; each was refused with "requirements not met". The original checks a skill's StateType column against the form word of the player in its skill check (GameServerRelease 0x890B30): type 1 needs the normal form (1), type 2 the Wild Mutation form (4), type 3 the Metamorphosis form (8), type 5 the Beast form (0x40), type 4 the normal or disguised form (1 or 0x10), and a failure sends 0x01E4 with 0xE (type 1) or 0xF followed by the refusal 0x00EF 0xF. I only let types 0, 1 and 4 through whatever the form, so Raging Nail (type 2) and Wild Nail (type 3) were always refused. The check now compares the type with the real form of the player (Wild Mutation, Change, Beast, disguise or normal), at the request and again when the cast ends, and a normal skill used while transformed is refused with the original's notice. In the game with the original client a Cat transformed with Wild Mutation (the server applied the form, the stats and the MP drain) and the client accepted the request of Raging Nail, which the server answered with the target request; I could not drive the target click in the harness, so the refusal at the end of the cast is covered by unit tests only, not checked in the game. Not yet checked: Metamorphosis and Wild Nail.
- Walking through walls in Megalopolis Guild Office and Rose Garden Park (issue walls): when a click needed a long detour around a wall, my path search found the way but the client's own search gave up and walked straight toward the goal until it stood at the wall, so the server believed the character was somewhere else. The next click then made the client draw a straight line from where it stood to the server's position, through the wall. The original server and client both search with a pool of 256 nodes (SmartPathFinder constructor 0x41A190 and 0x41AEC0 on the server, the client constructor 0x409D40 stores 0x100), fail the whole search when the pool is empty (0x41A790 with 0x41AF50), expand the neighbours in the order x then y from -1 to 1 (0x41A790), cost every step 2 (3 on a marked cell) plus 1 for a change of direction (0x41AD00), keep the open list sorted by f with the newest node first among equals (0x41AA60) and re-parent known nodes (0x41A850, 0x41AB20), then fall back to the greedy walk (0x41B160). I used a 4096-node limit with different step costs, so I now do the same search as the original and my position and the client's agree.
- Endless Harcon Defence monsters that never moved (issues 62, 126): in the Endless stage (25, map 667) the wave table Sc_HarconDef_Endless holds a group per five odd waves with Rpos 1 and Lump 18 where its neighbours read Rpos 18 and Lump 1, so ten monsters of those waves spawn on the point of the first Harcon, inside the blocked ground around it, and the route search found no way out of blocked ground, so they stood still. A monster that starts on a blocked cell now walks straight to the nearest free cell and routes from there. - Drill given with the GM tools could not be taken out of the MyShop box (issue 130): the box listed a rare item with its stored attribute as the count, which for a GM-given drill is the drill life (300 for drill 8001), while the original's take check compares the requested count with the rare item's own count, which is always 1 (GameServerRelease 0x6DE880, used by the take check 0x873470, see analysis/cash_box_wire.md section 2). Every refusal shows the same weight message in the client (0x0150 carries no reason), so a take with a count other than 1 looked like a weight problem. - EXP events that could not be changed or deleted (issue 131): planning an event again with a new percent (200 to 300) added a second event next to the first, and the server applies the first running event, so the rate stayed at 200; deleting asked for all four values to match, and the panel's start time defaults to the next full hour, so the second try missed the event. - Dropping an item (issue 134): an item you drop from the bag now flies toward the mouse cursor, as in the original, instead of landing on your character. I had treated a far cursor as "land on the character", which is what you saw. Not checked in the game.

In the original the scan (0x4243C0, the 500 ms tick, strategy byte +0xC4) starts the attack without asking for the limit; the limit (0x4240A0, set up at 0x4235E0 from the zone row type 1 / 2 or from DoesCntMonRetr and RetrMonNum, default 5) is only consulted when the monster is hit by a player (event 4, skill 0x7532), where being at the limit takes the 0x7553 branch instead of the retaliation. The scan now engages without the limit and the hit still respects it. Not yet checked in the game.
- Gun shots check the key the client echoes: the original server answers every gun shot request (C2S 0x01DD) with a new key (S2C 0x0200) and drops a request whose check word does not equal that key folded with the gun's GaugeSpeed, PowRange and PowStartPoint columns (GameServerRelease block 0x744F8A). On the original client the word is key xor (PowStartPoint shl 5) xor (PowRange shl 8) xor (GaugeSpeed shl 12), with bit 0 set when the charge gauge is inside the power window: for gun 3500 (150, 180, 85) it is key xor 0xF6C0 in the ten shots I recorded, before and after a map change, and the server dropped none of them. - GM cash box delivery: Give Item in the GM window has a Send to the cash box checkbox (on by default for cash items) and an Hours box, `tposeidon gm present-box <name> <itemId> [count] [hours]` and `@cashitem <itemId> [count] [hours] [name]` do the same. The item goes into the account's cash box like a bought one, so a timed item arrives with its real period (hours given, else the period the item has in the item shop, else no limit) and the client gets the timer when the player takes it out. The original has no direct path that puts a timed item in the bag together with its timer; only the cash box and the grant frames of shops and quests carry one.
- Fixed: the mailbox did not open and the chat said "Downloading Friend list.." forever with the original client. The system server address the channel server sends (opcode 0x1585) padded the host to a fixed 15 bytes, but the original client reads the host as a NUL-terminated string, so it took the zero padding as the port and never connected to the system server (no friend list, no mailbox, no guild or party). The host is now sent as a NUL-terminated string followed by the port and the session token.
- Friend server: a friend-list request without a social session is logged. The mailbox opens only after the friend list has arrived (see SYSTEMS.md).
- Fixed: a client that has only `data/libconfig_eng.dat` (and its `.idx`) closed right after Play when that file held Korean text, because the Automatic language then started the client in Korean mode, which loads `data/libconfig.dat`. Play now makes the files of the mode it starts: Korean mode gets `libconfig.dat` and `libconfig.idx` as copies of the English-named pair, and English mode still gets its files from the main pair. You do not need to keep both sets, and files the client has are never replaced.
- Fixed: with a Korean `libconfig.dat` next to an English `libconfig_eng.dat`, the client showed the English text but the game server and system server read the Korean file for monster, drop, guild and card text, so those names did not match (shown as `?????` or garbage). The servers now read the very file the client loads in the chosen mode.
- Automatic language looks at the file the client will load: English mode when `libconfig_eng.dat` is not Korean, Korean mode otherwise. Play writes the chosen mode and the reason to the panel log (and the console for `tposeidon play`).
- Server data is rebuilt when the client file it was built from changes (the data stamp now holds a checksum of that file), for example after changing the Client language or swapping the translated file.
- The panel's "..." menu shows **Client language** while the quick-access bubble is on, as the bubble does, with the same choices and current mark.
- GM eagle forms: the GM eagle can switch between its walking form (sword and shield) and its flying form (wings) with `tposeidon gm fly on|off`, `@fly on|off` or the Flying form and Walking form buttons of the panel's GM window; the server also answers the original's switch request (C2S 0x04B3). The original has no female GM eagle, so there is no such choice
- GM set level: `tposeidon gm set-level <name> <level>`, `@level <level> [name]` and a Set level button in the panel's GM window raise an online character to a level (1 to 400). It runs the natural level-up code, so a jump of N levels gives exactly what N level-ups give: 4 bonus points per level, the stat growth of the character's type, full HP and MP, the level-up gifts of every level passed, and the same frames to the client, which shows the new level, points and stats without a relog. The exp starts at the beginning of the new level. A lower level is refused: the original has no way to lower a level.
- GM learn skill: `tposeidon gm learn-skill`, `@learnskill` and a Teach button with a skill picker (names and icons) in the panel's GM window teach an online character a skill at a chosen level without TM points or a card; the client gets the same skill frames as for a skill scroll and the skill is saved
- Talk script calls with parameters: the server now answers the client's typed script call (C2S 0x0123); the exit function closes the dialog and every other function is refused with the empty answer, as on the original server
- Skill requests: a stunned character's skill request is answered with the cast-cancel frame (0x00F3), and a refused skill scroll with the empty item refusal (0x005A), as on the original server
- Megaphone queue: a shout is kept in the database by the master server, which sends one shout at a time to the system server, one `MegaphoneDelay` apart (18000 ms, the value in the original master server's ini file; it can be set in `MasterServer.ini`, and 0 turns delivery off). The next shout waits until the system server has answered the previous one. The shout window answers the number of shouts still waiting before yours instead of 0. A shout that is still queued when the master server restarts is cancelled and the megaphone is given back to its sender, as the original does. The system server repeats a failed send to a player up to three times
- Guild chat: lines typed in the guild chat tab reach every online member of the guild, as on the original system server
- Party member bars: the game server sends each party member the other members' hit points, mana, level, maximum hit points and maximum mana as they change, so the bars in the party window fill and follow, as on the original game server
- Party level-ups: the whole party is told when a member levels up and the by-level exp split is recomputed; the second pair of member marks is relayed; clearing a mark announces the member's map again; entering a map brings a dead member back into the exp group
- Guild notices: adding and deleting guild notices works, every online member sees the change at once, and the guild state at login lists the three newest notices
- Fiesta and other timed-map portals: a click on a portal of a Fiesta map (the client's new portal request) now takes the character through the portal the same way the ordinary portal click does, including the case where the character already stands in the portal area; before, that click answered the notice but did nothing when no walk was needed
- Portal clicks: two portal areas of one map that share a region id are no longer taken for the same portal when the character walks to the clicked one
- Login position: a character saved on a cell the map marks in its second cell layer, or strictly inside a portal area, is moved to a restart point like the other refused positions
- Monster walking: a map cell marked 2 no longer blocks a walking monster or its destination, as on the original servers (only cells marked 1 block the path; cells marked 3 are refused as a destination)
- My Camp starter items: the first character an account creates also puts the original's starter set into the account's My Camp: 13 default items and 3 random ones from a pool of 14 (once per account)
- Signed updates: every launcher update you publish is signed with a key made on your server (`launcher-signing-key.json`, also copied into every backup). Launchers you build carry the public key and refuse unsigned or wrongly signed updates. The open launcher shows whether a server signs its updates. **Change the signing key...** on the Publish page and `tposeidon launcher key` / `rotate-key` manage the key; launchers you already handed out follow a key change.
- Launcher self-update: hand out the launcher the wizard built (**Hand it out as an update**, the Publish page, or `tposeidon launcher publish --launcher <zip>`) and your players' launchers download it, check it and restart into it. The earlier launcher is kept for **Go back to the earlier launcher** in Options. A failed swap leaves the old launcher in place with a message.
- The built launcher and setup program show your server's icon in Explorer and carry your server's name in their file details instead of tPoseidon's.
- Test launchers (built for this computer) are marked, and the panel and `tposeidon launcher publish` warn when one is added to the updates or published.
- Party follow through a portal: a follower who cannot use the portal the member took is told so (code 5 when the portal's time window is closed, code 4 when his level is outside the portal's level range) instead of being sent after the member.

## 0.55.0-beta

The first public beta, released as v0.55 Beta. It targets the KR 2014 client. [docs/beta/SYSTEMS.md](docs/beta/SYSTEMS.md) has the full list of what works, what needs testing and what is missing.

### Setup and hosting

- Release packages for Windows (x64), Linux (x64 and arm64) and macOS (Intel and Apple silicon). They carry their own .NET runtime; you only install PostgreSQL.
- `tposeidon` command line: `setup`, `start`, `stop`, `status`, `backup`, `play` and `gm`. Setup asks where your client is, creates the database and reads the game data it needs from your client. Nothing from the game is shipped.
- A control panel (Windows) with setup, start and stop, backups, a log view for every server and a security window.
- Setup creates your first account and sets it as the account Play logs in with. Play gives the client a one-time login ticket, so the client's automatic login only works for the computer that pressed Play.
- Connection guard for servers open to the internet: connection and packet limits, timeouts, login throttling and temporary bans. See [Hosting securely](docs/install/hosting-securely.md).
- Every package comes with a manifest and SHA-256 hashes, and the build version shows in `tposeidon status` and the panel.
- Database changes apply on start, each one only once. `tposeidon start` warns first and offers a backup.

### Accounts and characters

- Login, server list, channel list, character creation, selection and deletion.
- The channel checks the client version and the login that came from the lobby, and refuses others with the original error codes. Blocked, penalized and already-logged-in accounts get the original refusal messages.
- Chat, trade and move blocks that are still running are handed to the client at login.
- Looking at another player's profile and equipment, and the options that hide them.

### World and combat

- Combat with melee, hammers and guns, damage, monster deaths, drops and pick-ups, experience and level-ups, death and restart in town.
- No caps on the server: damage, HP, MP, EXP, TM EXP and Galder are 64-bit on the server and in the database. The client shows at most 2,147,483,647 of any value, and the server sends that maximum instead of letting the number wrap. Optional limits are in `data/server_rates.json`, where `0` means no limit.
