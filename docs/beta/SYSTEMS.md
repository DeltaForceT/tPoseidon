# tPoseidon beta: system status

Last updated: 2026-10-30

This is where we say what works and what doesn't. The target is the KR 2014 "Original" variant: the aim is to behave like the original server, not to invent new rules.

Three lists:

1. **Working** - built and confirmed in live play with a real client.
2. **Built, needs testing** - built and passing our own tests, but nobody has played it live yet. Expect rough edges. These are the ones we most want you to try.
3. **Not built yet / partial** - known gaps. No need to report these as bugs.

Three systems are marked **reconstructed**: Harcon Defence, the slide-puzzle shuffle and pet collection. The original server code for these isn't available, so behaviour may differ from the original.

How to report a problem: see [how-to-report-a-bug.md](how-to-report-a-bug.md).

### Maps and line of fire
- Line of fire: gun shots and the skill Beast Claw read the height layer of the map (the fourth layer of the map file) and apply the original's rule: the line is walked in cells of 16 units, the highest cell is compared with the start and end cells. A snapshot built before this version has no height layer and is flat, so nothing is blocked until the world snapshot is built again. Other callers of the same test in the original (the skill check of a monster action) are not built
- The shot swing before a blocked gun shot and the unanswered rule of what the shooter does next (the original leaves its attack order as it was) are not read further: a blocked shot ends the order here
- Card battle title near a portal or an NPC, shop or skill shop point: refused with S2C 0x01D5 code 1 (portal area) or 2 (point), as the original. Only a field zone takes the request: the KR Server handler 0x73CA10 does everything under zone+8 == 1 (1 is a field zone, 2 a camp shell, per the My Camp enter and leave checks), so in a camp shell the request is ignored with no refusal and no title. The margin around the area is the original's constant
- Not built: the skill notice 0x02EC `[u16 skill id][u8]`. The Taiwan server sends it to the caster when a skill use passes every check, just before the skill action starts (sender 0x5A1F30 from 0x510210, after 0x67E1D0 returns -1), and the client reads the id, drops the byte, resets its pending action and shows the skill name followed by three exclamation marks (case 0x2EC of 0x6B4E00). The byte is stack residue in the server (the call at 0x5103FD pushes only two arguments) and carries no meaning. It stays unbuilt because the client call cancels the action in progress and its place among the target request, aim and self cast frames of the existing skill flow cannot be taken from the code; a capture of an original skill use is needed first
- Card battle title near a portal or an NPC, shop or skill shop point: refused with S2C 0x01D5 code 1 (portal area) or 2 (point), as the original. The margin around the area is the original's constant
- Not built: the skill notice 0x02EC `[u16 skill id][u8]`. The client reads the id, drops the byte, resets its pending action and shows the skill name followed by three exclamation marks (case 0x2EC of 0x6B4E00); the byte is stack residue in the server (the call at 0x5103FD of the Taiwan server pushes only two arguments) and carries no meaning. The KR Server sends it from one place only: 0x5ED750, called only by 0x75F340, which is called only by 0x41BD00 inside the player attack swing 0x41B970 (NormalAttackStrategy), where the skill held by the player's attack holder (player +0x918) passes the gate 0x890B30 (-1) and is followed by the action start 0x890E60 (the Taiwan twins are 0x5A1F30, 0x510210 and 0x891840). The skill-use order from C2S 0x00EE (0x75EBC0: checks, target request 0x00F1, gate 0x890B30, then 0x00F0 and the action start 0x8911A0 to 0x5BE9A0) never calls 0x5ED750, so the notice does not belong to the existing skill-use flow, and nothing says which of our skills run through the swing holder. It stays unbuilt until a capture of an original skill-attack swing shows where the holder is set and what the player sees

## 2. Built, needs testing

A short "try" hint is given where one is obvious.

### Account and characters
- Channel login check: the character list is only sent to a client that logged in on the lobby and picked a server; the channel checks the lobby's authcode as the original servers do and refuses others with the original error codes (60100 unknown account, 60101 wrong authcode, 60102 no server picked). A second login of the same account on the channel closes the first one - try logging in twice from two clients. The channel also checks the client version as the original LoginServer does (the KR 2014 client's version by default, `Version = major.minor` in LoginServer.ini for another client) and refuses a missing or different version - start an older or newer client against the channel
- Waiting at character select: the channel pings the client every 60 seconds like the original LoginServer; a client that stops answering is disconnected - leave a client at character select for 15 minutes
- Lobby login refusals: a wrong name or password, a blocked account and a withdrawn account get the original refusal code instead of a dropped connection; a penalized account sees the penalty name and its release time and cannot log in until the penalty ends (operators add penalties with `tposeidon gm penalty-kind`, `penalty-time`, `penalty`, `penalty-release` and `penalty-list`); an account that is still logged in elsewhere is refused (60013), as on the original servers - log in twice with the same account, and penalize a test account
- Account login states follow the original servers: the lobby clears states left by a crash when it starts and when a player leaves the lobby before picking a server, the channel login moves the account to "in game", and a channel restart or leaving the channel before choosing a character logs the account out
- A character pick that the game server never joined (client closed right after the channel hand-off) releases the account after 30 seconds (**reconstructed**: the original LoginServer logs the account out when its connection closes and has no other timeout for the in-game state; the channel here hands the client over to the game server and drops the link, so the 30 second window is our own) - test: pick a character, kill the client before it enters the game, and log in again after 30 seconds
- Blocks at login: a chat, trade or move block that is still running when the character is selected is handed to the client with its minutes left, as on the original servers, and the client keeps counting it down - block a character for chat, relog, and try to chat
- Second password (the padlock), at character select: a new account gets the question "create a second password?" about half a second after the character list (it is the client's own default when the server sends no padlock record); Yes opens the create window (4 to 6 characters, same twice, an email), which answers "password updated" and stores the record locked with all three guards (bank and storage, shops and trade, MyShop and guild). On the next login the server sends the stored email, state and guards before the character list, and a locked account sees the locked notice. The change window needs the old password (wrong old password, wrong password, wrong length and wrong action get the client's own messages). Deleting a character asks for the second password only while the lock is on, and a wrong password refuses the delete with the "wrong password" message. Read from the original LoginServer and MasterServer (request dispatcher, the master's three commands and the three stored procedures, also in the Taiwan database) and from the 2014 client (the views, the request gate, the message handler). Not yet live-tested. Check with a fresh account: create the password, relog, change it, delete a character with a wrong then a right password. In the game world the same envelope is checked by the game server as the original does: while the account is locked and the command's guard is in the account bitmask, the hashed password must match, else the client gets the wrong-password message (0x03A1 code 1). Guard 2 (shops, trade, throw, sell, post, recycle, player shop): commands 0x43, 0x4C, 0xAC, 0xB0, 0x15B, 0x163, 0x3F1, 0x3F5, 0x3F7, 0x4D4, 0x4D7, 0x4DA; guard 1 (bank and storage): 0x2FE. The in-game padlock window (set, change, lock, unlock) uses the same service. The bank and storage (guard 1) and MyShop and guild (guard 4) requests are NPC script calls: the client tunnels them as inner command 0x7F, and the guard is read from the call's function number (0x10 and 0x11 for guard 1; 0x35, 0x36 and 0x4F to 0x51 for guard 4). They are checked first and then run through the NPC script handler as before. Not built: command 0x2FE (guard 1, sent with one 16-bit value, purpose not determined), which the game server has no handler for yet; command 0x52C is gated by the client but the original game server does not list it; the client's bitmask change request (0x808) is never sent by the 2014 client. **Reconstructed** (no source): a hash that is not 16 characters is refused as wrong length; changing with no record or a disabled lock is refused as wrong action; the lock-disable request from an empty state fails in the database as the stored procedure does for a missing row.
- Stat point spending - spend points after a level-up, then relog to check they stuck
- Relogging with HP and TM exp saved - log out mid-hunt and log back in
- Selecting a character that is not one of the account's slots answers the client with the original refusal code instead of leaving it waiting on the connecting screen

The original server has no sender for the compound start-failed, compound abnormal-end, exchange start-failed and exchange abnormal-end replies, so none is sent
- Repair of broken equipment in the refine window: the material and the count come from the RepairInfo table of the data files, by the item's refine level, type and sub type (repair powder as many as the refine level for ordinary equipment, one phantom powder for neo equipment; an item kind that has no row is refused as impossible)

- Equipment decomposing (NPC function 255): with one Craftsman's Flame a composed item gives its look back as a new item (the look's own item when it may come back, otherwise the dummy skin of its kind from DecompoundDummyItem carrying the look) and keeps its other properties
- Pet composing (NPC function 212): the first pet keeps its stats and takes the look of the second pet, which is used up together with one pet composing book; the second pet's level must be at least the first one's; the gift item of PetComposingPresentInfo is given afterwards, as on the original servers

- Equipment Recycling (NPC service 206): items to recycle coupons (the client sends the request inside the password tunnel, C2S 0x039F, inner 0x03F1; the coupon exchange 0x03F7 and camp recycle 0x03F5 travel the same way; every refusal is answered)
- My Camp Recycling (NPC service 207): camp items to recycle coupons, one coupon each
- Timed items counting down and expiring
- Speed byte (S2C 0x01D8 and the spawn speed bytes): speed divided by 4 and truncated. Per the KR Server GameServerRelease.exe 0x60C750: FDIV by the double 4.0 at 0x988970, then FNSTCW, OR 0xC00 into the control word (round toward zero) and FISTP, so the base player speeds walk 115, run 184 and chase 150 of MoveSpeedParam row 1 send 28 (0x1C), 46 (0x2E) and 37 (0x25). The pseudo code of the decompiler shows this as a rounding; the instructions truncate.
- Character data frame (S2C 0x02A7): 73 bytes (the original copies 73 bytes from the login info at +0x13; the client reader copies the first 0x45), ending in an 8 byte time at +0x2D, the creation time of the character (char_attr.gen_time) as seconds since 1970. Per the KR Server GameServerRelease.exe 0x5F6960 (the sender: 73 bytes copied from the login info at +0x13), the column order of uspt_select_char_all (type, job, f_type, pts_p, pts_m, pts_s, pts_c, gen_time) and the reader 0x89C910, which takes the days since the time at +0x2D with __difftime64. The character record the Master fills (MasterServer.exe 0x44B920, cCharStore::LoadChrInfo, columns of uspm_char_all_select_char_info_improve) ends with couple_code, a bigint bound as 8 bytes at +0x41 after soulseed_flag (+0x3F) and awakening_flag (+0x40); the last four bytes of the frame (+0x45..+0x48) are the high half of that code, 0 for the int couple codes of the tables. Ours sends them as zero; the same 73 bytes start the growth reset answer S2C 0x0289.
- Timed item registration frame (S2C 0x0324): `[u32 count][count x 21 bytes]`, each `[u64 item uid][u32 item id][u64 expiry as a Windows file time][u8]`. Per the Taiwan server's GameServer.exe 0x5A3CF0 (the sender, reached from the shop buy 0x522C00, quest finish 0x52DA80, item exchange 0x531680, present 0x5325E0 and three more) the first three fields are the item's uid and id and the expiry the Master returned, and the last byte is copied from a stack slot that none of those callers ever writes, so it carries no value and we send 0. The frame is built (`TimedItemFrames.Registered`) but no grant path of ours sends it yet, because our grants other than the cash box (which carries the same record in its own take frame) and the recharge do not give an item an expiry; the original gets the expiry from the Master stored procedures (a time is added only to rare class items whose item list row has AddMinute above 0, `USPM_ItemTrade_Shop`, `USPM_Recv_PostItem`, `USPM_Send_GMGiftItem` of the Taiwan database script), and the table the game server fills AddMinute from is not yet read
- Timed item grants: the period of a time-limited item (item data ExistType 1) is the Minute of its GeneralTimerItem row, 0 when it has none. Per the KR Server GameServerRelease.exe 0x633C00 (the period getter: item info +0x40 must be 1, then the GeneralTimerItem hash by item id, else 0), used by the grant paths at 0x5EF810, 0x5EF9A0, 0x5F16C0, 0x5F1F60, 0x60A740 (GM gift), 0x60B2E0, 0x60B420, 0x60B5B0, 0x78BC80, 0x794470 and 0x795970. The Master stores item_breaked = now + minutes for class 2 only (the Taiwan SQL item trade, post receive and GM gift procedures) and returns the expiry u64 in its reply; the shop buy at 0x7726D0 registers each item whose reply u64 is not zero (0x6EE410) and sends 0x0324 (0x5EF510) after the bought-items frame. Ours: ItemManager.GrantRewardItem stores the expiry (new item store call SetBreakedAt, Master sub-op 0x0C); shop buy, quest and job-change rewards, the exchange shop and NPC-issued items send 0x0324 after their bag frame; the GM present into the bag takes optional Hours (wire mode byte 2), a trailing choice of ours that the original tool does not have. Flows of the 0x633C00 callers (KR Server): 0x5EF810 is the shared inter-server 0x1047 of the exchange shop, the egg shop and the gift box (the OnOk handlers 0x780A90, 0x78C850 and 0x7819A0 send 0x0324 before their result frame), 0x5EF9A0 the shop buy, 0x5F16C0 the quest finish, 0x5F1F60 the party quest reward, 0x60A740 the level up gift mail (Master 0xC51), 0x78BC80 pet level up, 0x794470 pet merge, 0x795970 equipment merge, and 0x60B2E0, 0x60B420, 0x60B5B0 (inter-server 0x10A9, 0x10AC, 0x10AF) are the item-use handlers 0x796D50 (C2S 0x0503, item Effect 47, jump table 0x75A324 with byte table 0x75A3B0 of the dispatcher 0x73D2A0: opcode = 0x414 + index, slot 29), 0x797590 (Effect 48, C2S 0x0509 by the slot order and the pet note) and 0x797E00 (C2S 0x050F, Effects 49 and 50: the key box confirm, which ours has). The first two roll PresentItemParam2 items with the gift box generator 0x6DFD80 and are not built (the meaning of their u64 target is not captured); their OnOk handlers 0x7970E0 and 0x797940 send 0x0324 as the others do. Compound has no timer (npc_services_server.md section on compound OnOk). Egg shop and gift box send 0x0324 as the exchange shop does; the take of a post carries the expiry in the u64 after each item of S2C 0x04D5 (the client reads it with the same registration routine as the 0x0324 case, 0x595C10), so no 0x0324 follows it. Pet level up, pet merge and equipment merge (OnOk handlers 0x78BF00, 0x794800 and 0x79C470) send the period of the created item (0x633C00 of the result) in the equipment upgrade message: ours carries it as a new field of each inserted row and the Master stamps item_breaked for class 2 as above, returns the expiry in the reply row, and the game server sends 0x0324 before the result frame (S2C 0x0371, 0x04BB, equip merge result). The key box confirm (OnOk 0x7984B0) sends one 0x0324 per timed prize, before the window closes and the result. Items with ExistType 1 and no table row (for example 19028 and 19030) are given without an expiry, as the original does, and the client shows them as expired.

## 4. Value limits

The server does not cap game values. Damage, monster HP, player HP and MP (current and maximum), Galder carried and in the bank, EXP, TM EXP and the pools of shields and effects are calculated and stored as 64-bit numbers, and the database columns for them are 64-bit. A hit of 9,000,000,000 takes 9,000,000,000 HP off the target, and a wallet can hold more than 2,147,483,647 Galder.

What limits a number is the client, which cannot be changed in the Original variant. Whatever the server holds, the value sent to the client is cut at the largest number the client reads and never wraps around:

- Every number the client reads as a 32-bit value (damage in the hit result, monster HP, player HP and MP, EXP, TM EXP, Galder in the wallet and in the bank window, quest rewards) is read as a signed number, so the largest value it can show is 2,147,483,647. Above that, the server sends 2,147,483,647 and keeps the real value.
- The attack packet (0x001F) carries a 16-bit damage field. The client never reads it, so it is cut at 32,767 without any visible effect.
- The client works out maximum HP and MP itself from the stat points and clamps the current HP and MP it is sent to that maximum. A monster's HP is clamped to the `MaxHpLv` of its entry in the client's own MonsterParam table, so an HP bar above that value needs the client's table changed too.
- Stat points are 16-bit in the client (65,535 per stat), item stacks are 16-bit (65,535), and the client's level and EXP tables stop at level 400 (TM level 500). The server keeps these limits.
- The client refuses actions above 2,100,000,000 Galder in its own windows (Gelder coupon, selling to an NPC shop, mail attachment, number input). Trades and player shops settle at most 2,147,483,647 Galder because the amount is sent to the client.

Optional limits are in `data/server_rates.json`, section `Caps`: `MaxDamagePerHit`, `MaxHpPool`, `MaxMpPool`, `MaxGalder` (carried) and `MaxBankGalder`. `0` means no limit and is the default. Files written by older builds contain explicit limits (65535 for damage, 4294967295 for the pools), so set those to `0` to remove them; the control panel's Caps group does the same.

The update adds database migration 075, which widens `characters.hp`, `characters.mp` and `characters.tm_exp` to 64-bit and replaces the upper bound on `characters.money` with a plain "not negative" check. No stored value changes. Back up first, as with every update.
